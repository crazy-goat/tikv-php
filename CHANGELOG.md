# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).
Before `1.0.0` a breaking change bumps the minor version, so a `0.x` release
may break your code. From the next release onwards the entries of this file
mark a breaking change in one of two ways:

- **BREAKING** — the change breaks the public API surface named in the
  [stability policy](README.md#stability-and-versioning). It carries a
  migration note.
- **Breaking change:** — the change breaks a class outside that surface (an
  internal extension point). It carries a migration note and needs no version
  bump of its own.

The entries released before this policy keep the wording they shipped with.
The two v0.4.0 entries marked **BREAKING** were marked when the policy was
published, so that a reader who searches for the marker finds the breaks of
that release too: they broke classes of the `RawKv\` namespace, which the
policy now classifies as internal.

## [Unreleased]

### Added

- `begin()`, `beginOptimistic()` and `beginPessimistic()` accept `optimisticLockTtlMs` (default 3000, the baseline of the per-mutation scaling) and `pessimisticLockTtlMs` (default 30000). A pessimistic transaction now extends its primary lock automatically: `get()`, `batchGet()`, `scan()`, `set()` and `delete()` send a `TxnHeartBeat` when less than half of the lock TTL remains. An optimistic transaction holds no lock before `commit()`, so it sends none. A transaction that waits without touching TiKV still needs an explicit `heartbeat()`. (#429)
- `RawKvClient::reapIdleChannels()` and `TxnKvClient::reapIdleChannels()` drop the cached gRPC channels that were idle longer than `idleTtlMs`, so a long-running worker that is quiet for a long time can reclaim them from its own tick. The call sends no RPC and is a no-op after `close()`. (#277)
- **Breaking change:** `GrpcClientInterface` gained `reapIdleChannels(): void`; an own implementation must add this method (an empty body is enough when it caches no channels). `GrpcClient` and `ApiV2GrpcClient` already have it. (#277)

### Fixed

- Lock TTLs now include the time the transaction has already run, because TiKV counts a lock TTL from the start timestamp. Before, a pessimistic lock taken, an optimistic prewrite sent or a heartbeat issued after more than one TTL of uptime carried a plain TTL: the locks were born expired and the heartbeat did nothing. Pessimistic-lock requests, prewrite requests and heartbeats now carry `min(uptime + TTL, 1 hour)`. `Transaction::heartbeat()` without an argument asks for `uptime + TTL` instead of a fixed 10000 ms, and a pessimistic `commit()` sends a heartbeat first when less than half of the TTL remains. (#429)
- `GrpcClient` now also sweeps idle channels on the cache-hit path of `getChannel()`, so the cached handles of stores that left the cluster no longer stay in the cache for ever in a client that only reuses cached channels (the sweep used to run only before a new channel was created). The sweep drops the cached handle and frees its slot; the ext-grpc persistent channel and its connection can outlive the handle. The sweep is rate limited to one run per `idleTtlMs / 10` (at least 1 s, at most `idleTtlMs`) and never closes the returned channel or a channel with in-flight calls. `GrpcClient::reapIdleChannels()` lets a long-running worker trigger the sweep itself. `GrpcClient` takes an optional `clock` closure for tests. `maxChannels` now evicts down to the cap in one call instead of one channel per new address, and the soft-cap warning is logged once per overshoot instead of once per new address. (#277)
- `docs/operations.md` now has a Limits section with the real key, value, scan and batch constants and the exception that the client throws. It states that batches split automatically per region. `docs/advanced.md` no longer shows the redundant `BatchOptimizer` class, and the Best Practices examples no longer advise manual chunking. (#398)
- `docs/configuration.md` now states the real log levels and shows sample log lines that exist in `src/` (issue #380, DOC-14). Region cache hits and misses are DEBUG records, not INFO. The invalidation record is `Region invalidated` with a `regionId` field and no `reason`. The sample keys use the `KeyRedactor` format. (#380)
- `ScanIterator` now throws `TiKvException` when a page does not move the scan cursor forward — its last key does not advance the cursor, or its first key lies before it — instead of looping forever on a server that keeps answering a full page ending on the same key. Any forward scan was affected, bounded ones included (a constant last key keeps the cursor below `endKey`). Well-behaved servers return strictly increasing keys and are unaffected. (#312)
- The repository now commits `composer.lock` (resolved with `config.platform.php` set to `8.2.0`, so it installs on PHP 8.2 to 8.4), the Dockerfile copies it before `composer install`, `make clean` keeps it, and the CI `lint` job runs `composer audit --locked`. `squizlabs/php_codesniffer` is raised to `^3.13.6 || ^4.0.2` (CVE-2026-67434). (#311)
- `TxnReader::executeScanForRegion()` now re-asks a `KvScan` sub-range once when it answers an empty batch while the scan limit is still unsatisfied, instead of silently returning zero rows (or a truncated range, for the truncation probe) on a one-off empty answer. A scan of an empty range now sends one extra RPC. (#512)
- The V1 batch fan-out (`RawKvBatch` batchGet/batchPut/batchDelete) now dispatches every sub-request through `GrpcClient::callAsync()` instead of hand-rolling `\Grpc\Call` on a raw channel from `getChannel()`, so its calls are counted as in-flight and an LRU/idle channel eviction can no longer close the channel under them. Every RPC sent through `GrpcClient::callAsync()` — the V1 batch fan-out, the TxnKv prewrite/commit fan-out, scans, range operations and SST ingest — is now visible to `MetricsInterface`: `callAsync()` emits `rpcStarted()` and, when the future settles (once, also on cancellation), `rpcCompleted()`. Expect new operation tags (e.g. `tikvpb.Tikv/RawBatchGet`) and higher RPC counts. The batch deadline is now derived by `callAsync()`; `RawKvBatch::deadlineFor()` is gone. (#273)
- `GrpcClient::call()`, `callStreaming()` and `callAsync()` no longer let a metrics backend that throws from `rpcCompleted()` replace the transport exception that is propagating; the backend error is logged at warning level and swallowed. `call()` and `callStreaming()` already cover channel acquisition, call construction and the send phase with the same `try`/`finally` that records `rpcCompleted` (so `rpcStarted == rpcSucceeded + rpcFailed` for every terminated call); regression tests now pin exactly-once, `success = false` completion for a `getChannel()` failure and a transport failure, and the throwing-backend case. (#274)
- `RegionResolver::getRegionInfo()` now rejects a PD-returned region whose range does not contain the requested key, instead of caching it. The lookup fails with a retryable `RegionException` (`RegionNotFound`, `RegionMiss` backoff), so one stale PD answer during a split no longer causes a persistent fatal `KeyNotInRegion`. (#253)
- `RegionCache::put()` now ignores a region whose epoch is strictly older than the cached one for the same ID, preventing stale `scanRegions` results from downgrading a fresher entry. (#249)
- `TlsConfigBuilder::readFile()` no longer emits a PHP warning exposing the resolved certificate path when the file is unreadable. (#553)

### Changed

- **BREAKING**: the store cache of `PdClient` is now mandatory (issue #298, PERF-11). The fourth constructor parameter is `StoreCacheInterface $storeCache = new StoreCache()` instead of `?StoreCacheInterface $storeCache = null`, so a `PdClient` built with three arguments no longer sends one `GetStore` RPC to PD per store lookup. `ConnectionFactory` users see no change. **Migration:** do not pass `null` for the store cache; omit the argument to get the default `StoreCache`, or pass your own `StoreCacheInterface`. (#298)
- **BREAKING**: an option the client cannot apply is no longer silently ignored in `options['timeout']` and `options['slowLog']` (issue #272, GRPC-13). Both groups are now mapped from `TimeoutConfig`'s and `SlowLogConfig`'s constructor signatures, so every field is configurable under its own name and a field added to either class is configurable the moment it exists. An unknown key, a value of the wrong type, and a group that is not an array are all reported with an `InvalidArgumentException` that names the option — before, such an option was dropped and the built-in default applied, with no warning anywhere (a typo like `['ingestTimeout' => 300000]` instead of `['ingestTimeoutMs' => 300000]` silently ran with the 60-second default). An option group that is absent, or explicitly `null`, still means "not configured" and keeps the default. **Migration:** remove the unknown key(s) from `options['timeout']` / `options['slowLog']` or rename them to the exact field name (`ingestTimeoutMs`, `readThresholdMs`, …), and make sure every value is an integer — the client is now created only when every key and value in those two groups is valid.
- An unmapped `RegionException` (no typed `ErrorKind`) is now classified as fatal instead of `BackoffType::RegionMiss`, so permanent misconfiguration errors such as "invalid cf" fail after a single attempt instead of being retried 30 times. A per-pair `KeyError` is now reported as `KeyErrorException` rather than `RegionException`, so it is no longer retried as a region miss. (#251)
- **BREAKING**: a non-positive timeout is now a configuration error instead of "no deadline at all" (issue #276, GRPC-17). `TimeoutConfig` rejects a non-positive value for every timeout field, `ConnectionFactory` rejects a non-positive `options['timeout']` entry and names the offending key, and `GrpcClient::call()` / `callAsync()` / `callStreaming()` throw `InvalidArgumentException` for a non-positive `$timeoutMs`. `0` used to be the documented "no deadline" sentinel, but it is also what an unset environment variable coerces to (`(int) getenv('TIKV_READ_TIMEOUT_MS')` yields `0`), so a configuration mistake turned into a call that never expires — and a gRPC call that never expires cannot be interrupted by PHP. **Migration:** replace every `0` timeout with a large finite value; a gRPC call can no longer be unbounded.
- `batchDeadlineMs` is unchanged: it is a wall-clock budget for the batch fan-out, not a gRPC deadline, so `0` still disables it. The slow-log thresholds keep `0` as their documented "disabled" value and now reject a negative threshold. (issue #276)

### Tests

- `MemComparableCodec` is pinned to TiDB `codec.EncodeBytes`: known-answer vectors for `abc` and a two-byte key, group-boundary and seeded random round-trip and sort-order tests, and a marker-range rejection test. No production behaviour changes — #415 already implemented the scheme and wired the TxnKV region-key encode/decode (`PdClient::getRegion()`/`scanRegions()`, `RegionInfoMapper::fromProto()`). The issue quotes `6162630000000000f9` for `abc`; the correct marker is `fa` (pad = 5). (#252)

### Added

- `benchmarks/TxnCommitLatencyBenchmark.php`: the commit latency of a multi-region transaction, measured twice over the same client code path — once with the two-phase-commit RPCs fanned out across regions, once with one RPC at a time (the shape of the client before the fan-out). The fake store answers every RPC after a fixed latency, so the two columns differ only in WHEN the requests are sent: at 5 ms per RPC a 20-region transaction commits in ~25 ms with the fan-out and ~247 ms without it, while the RPC count is identical (20 prewrites + 20 commits). The fan-out itself was implemented in #291 (PERF-04); the benchmark is the measurement issue #431 (GAP-17) asked for. (#431)
- **CI**: the coverage CI already collected is now **enforced**. The `grpc-unit-tests` job runs the `Unit` and the `Grpc` suite together under PCOV (it already installs PCOV and `ext-grpc`), writes the Clover report to `coverage.xml`, uploads it as the `coverage-clover` artifact and fails the build when the line coverage drops below the floor. The floor is a **ratchet**: `87.0 %` against a measured `87.6 %` (PCOV, PHP 8.4 — the measurement moves with the tree, the floor only moves up), and it lives in exactly one place — `DEFAULT_COVERAGE_FLOOR` in the new `bin/check-coverage.php` — so the CI job and the new `composer test:coverage` script cannot drift apart; the composer script runs the same suites and applies the same threshold, which makes a red build reproducible locally. The measurement is the line coverage of the **hand-written** code: `phpunit.xml` now excludes the generated `src/Proto` classes from the coverage source set, because they are ~62 % of the executable lines of `src/` and nobody writes tests for them — the same run reports 42 % with them and 87 % without. The issue's own baselines (58.4 % for `Unit`, 70.2 % for `Unit` + `Grpc`) are not reproducible with the current tree: measured on the audit-time tree (2026-08-08) the whole-tree numbers were 14.6 % and 18.3 %, and the hand-written-code numbers 62.1 % and 78.0 %, so the coverage of the client grew by roughly 16 points since the audit. `tests/Unit/Bin/CoverageFloorCheckTest.php` pins the behaviour of the check (below the floor fails, at or above it passes, a missing or unreadable report is an error) and the ratcheted floor value itself. `phpunit.xml` also drops `ParallelRangeOpsCapTest` and `CheckedGrpcFutureRetryableDispatchTest` from the `Grpc` suite: a file listed in two suites that are selected together makes PHPUnit emit the test-runner warning "Cannot add file … as it was already added to test suite …" and the run then exits 1 even though every test passed. Both files are pure PHP and stay in the `Unit` suite, which the coverage job runs as well. (#362)
- `TxnKvClient::begin()` accepts a new `lockWaitTimeMs` option (issue #443, DIV-07): how long TiKV may wait for a contended pessimistic lock before it answers with a "locked" error. The value is sent as `PessimisticLockRequest.wait_timeout` — the field was never set before, so TiKV applied its own server default and the caller could not bound the wait. The default is 1000 ms, the same timeout TiKV applies by default (`pessimistic-txn.wait-for-lock-timeout`), so the behaviour is unchanged on a TiKV with that default; `0` restores the previous behaviour on any cluster ("let TiKV use its own default timeout"). TiKV caps the wait at its own `pessimistic-txn.wait-for-lock-timeout`, so a larger `lockWaitTimeMs` never makes the server wait longer than that. The effective value is `min(lockWaitTimeMs, remaining lock-wait budget)`: it never exceeds the budget and shrinks as the budget is consumed (client-go's `calculateEffectiveWaitTime`). The budget counts the client's backoff sleeps, not the time the lock RPCs themselves take, so the total occupancy of a contended key is the budget plus the server-side waits of the attempts. An exhausted budget still raises `LockWaitTimeoutException` — the transaction never proceeds to prewrite without the lock. (#443)
- **[DOC-41]**: the fail-closed TLS control and the gRPC channel-pool options are reachable through the public factory, and the transport ownership model is documented. `options['allowInsecure']` (available since #304) is joined by `options['maxChannels']` and `options['idleTtlMs']`: `ConnectionFactory::create()` — and therefore `RawKvClient::create()` / `TxnKvClient::create()` — forwards them to the `GrpcClient`, so the channel pool (default 64 channels, 10-minute idle TTL) is configurable without assembling the client by hand. ### Changed

- **[GRPC-24]**: the ext-grpc channel semantics behind `GrpcClient` are now **verified and documented** instead of assumed. ext-grpc keeps a **process-global** table of persistent channels whose key is `target + sha1(channel arguments) + sha1(credentials)`, so identically configured clients share one underlying `grpc_channel` — as long as the key is in that table: ext-grpc persists **one channel per target**, and a channel created beyond that bound is private to its handle (ext-grpc logs "The number of channel for the target is maxed out bounded"). `Channel::close()` is a **reference-count decrement** (`php_grpc_channel_unref()`), not a destroy: the underlying channel survives until its last holder releases it, and the persistent table is one of those holders — so closing one client can never destroy a channel another client holds, it only drops that client's own reference. Verified against the deployed extension (grpc 1.83.0, `src/php/ext/grpc/channel.c`; the persistent-channel code is unchanged in the oldest supported release, 1.57, so the statement holds across the supported range) and pinned by `tests/Unit/Grpc/GrpcClientChannelIsolationTest.php`, so a future extension that turns `close()` into a destroy fails the suite instead of silently breaking a second client. The same verification corrects two promises of `GrpcClientInterface`: `closeChannel()` drops the cached handle but does **not** force a reconnect (the persistent entry survives, so the next call reuses the same underlying channel and the same TCP connection), and `close()` releases this client's handles while ext-grpc keeps the connection warm in its process-global persistent table — it does not tear the connection down. `options['metrics']` is documented as what it is: a **client-side** option (region cache, retries) that is always applied, while the transport's own RPC counters follow the transport — with an injected transport they are the ones it was built with, and the factory says so in the log when the option was given. (#283)
- The parallel prewrite's aggregated failure is now reported instead of being dropped. When several regions fail, the fan-out collects every failure (it waits for its in-flight calls rather than aborting at the first one), and the summary — one entry per failed region, with the region id and the error — is logged before the error of the first failing region in dispatch order is rethrown. The rethrown error is unchanged (issue #291's first-error contract, which `docs/error-handling.md` documents for `Transaction::commit()`), but a multi-region failure no longer looks like a single-region one: the aggregate's own keys are group indices, which identify no region. Pinned by `tests/Unit/TxnKv/TxnKvFanoutTest.php`, which also proves the two properties the fan-out has to keep — a failing region does not cancel its peers, and the retry is scoped to the region that failed (its peers are not re-sent). The pessimistic-lock path is unchanged: its first attempts are already fanned out (#291) and its retries stay sequential by design. (#431)
- **[PERF-13]**: the region cache no longer builds a log context for a logger that cannot use it. `RegionCache` computed `KeyRedactor::redact()` — a `substr` + `bin2hex` + `sprintf` — and the surrounding context array before every `debug()` call, unconditionally: on every cache hit, on every miss, and twice per `put()`, even with the default `NullLogger`, which discards the record. The redaction is now computed only when the cache emits debug records at all, decided **once at construction, from the logger itself**: the new `DebugLogging::handlesDebug()` asks a logger that has a level API (Monolog's de-facto `isHandling()`) whether it handles the `debug` level, and falls back to the class otherwise — a `NullLogger` discards everything, and psr/log does not declare that class `final`, so only a logger that keeps psr/log's own `log()` **and** `debug()` implementations is treated as discarding; a subclass that overrides either method may record what it receives and is therefore assumed to handle `debug`. A logger above the `DEBUG` level (the "production" recipe in `docs/configuration.md`) therefore pays nothing either, which the first round of this change did not manage: PSR-3 has no level API, so the level is asked through the logger's own API and tolerantly — the level is passed in the shape the signature accepts (Monolog 2 takes an `int`, Monolog 3 an `int|string|Level`), and a logger whose `isHandling()` throws is reported as "cannot tell" instead of breaking the client. A logger that cannot be asked at all (a plain PSR-3 logger without a level API) is assumed to handle `debug`, so a record is never lost. **Behaviour change**: the client no longer calls `debug()` at all on a logger that is known to discard every record (the `NullLogger` and the subclasses that keep psr/log's own `log()` and `debug()`), and it no longer calls it on a logger that has answered "no" to the debug level (a Monolog logger above `DEBUG`), which used to receive the call and drop the record itself. A logger that may record keeps its records: a `NullLogger` subclass that overrides `log()` **or** `debug()` is not treated as discarding and receives the cache's debug records again (the first round of this change silenced it). The answer is frozen with the decision, and that is a behaviour change of its own: the logger is `readonly`, so it cannot be swapped, but its level can change at runtime and the cache does not ask again — a logger reconfigured at runtime (a Monolog handler lowered to `DEBUG` after the client was built) does not receive the records it used to get, so configure the logger's level and handlers **before** the client is built and create a new client after you change them. **No behaviour change when debug logging is enabled**: the records are still emitted with their full context. Measured with `php benchmarks/RegionCacheBenchmark.php` (100,000 `getByKey()` calls against a warm 10,000-entry cache): about 15 % less CPU on the development machine (11 %–20 % across runs; a median of 181 ms before the change against 147 ms after it in the run quoted here — the absolute milliseconds depend on the machine and its load, so only the ratio is comparable) — and the `put()` path 1.27 µs → 0.82 µs per put. The issue's acceptance criterion ("below 78 ms") is an absolute number measured on the issue author's hardware, so it cannot be compared across machines either; the benchmark now measures both shapes on the same machine (the guarded cache and a reference cache that builds the log context, as before this change) and prints the ratio it measured itself. ### Changed

- **[GRPC-01]**: every gRPC call now carries a finite deadline, and `null` no longer means "no timeout". `GrpcClient::call()` treated a `null` timeout as `Timeval::infFuture()`, and the three call sites that passed none — `PdClient` (all metadata RPCs, the cluster-id retry and the `GetMembers` leader discovery), `TimestampOracle` (every `Tso` request, so **every** transaction begin) and `LockResolver` (`KvCheckTxnStatus`, `KvCheckSecondaryLocks`, both `KvResolveLock` paths) — therefore ran with a deadline that never expired. `Grpc\Call::startBatch()` is a synchronous call into the gRPC C core, where PHP's `max_execution_time` and `set_time_limit()` do not reach, so a PD that became unreachable without a TCP reset (a network partition, a blackholing firewall, an overloaded PD that accepts connections and never answers) pinned a worker until the kernel gave up — minutes, or never — and in PHP-FPM exhausted the whole pool, stopping traffic that never touched TiKV. `TimeoutConfig` gains `pdTimeoutMs` (3000), `tsoTimeoutMs` (3000) and `lockResolveTimeoutMs` (5000), all settable through `options['timeout']` and all configured separately from the TiKV-RPC fields because a hung PD and a slow store are different failures: a hung metadata plane takes every lookup and every transaction begin down at once, a slow store is a per-region problem the retry executor already handles. The values are threaded into every `GrpcClientInterface::call()` in the three classes, and `LockResolver::checkTxnStatus()`'s TSO fetch now uses `tsoTimeoutMs` rather than the store `writeTimeoutMs`. **Behaviour change**: a call whose `$timeoutMs` is `null` now gets `GrpcClient::DEFAULT_TIMEOUT_MS` (30 s) instead of an infinite deadline, for `call()`, `callAsync()` and `callStreaming()` alike; the conservative default is a backstop, not the primary mechanism — PD/TSO/lock resolution name their own 3–5 s deadlines and a configured store timeout is still honoured. A caller that genuinely wants an unbounded call must now say so explicitly by passing `0`, the same non-positive sentinel `TimeoutConfig`'s `batchDeadlineMs` already uses for "disabled". `TimestampOracle::getTimestamp()`/`getTimestampBatch()`/`getLowResolutionTimestamp()` keep their optional `$timeoutMs` argument, which now *overrides* the configured `tsoTimeoutMs` rather than switching the deadline off. Regression coverage: `RpcDeadlineTest` drives `getRegion()`, `scanRegions()`, the cluster-id retry, leader discovery, failover re-discovery, `getTimestamp()`, the batch and low-resolution TSO paths, the TSO cluster-id retry, `checkTxnStatus()`, both `resolveLock*` paths and the async-commit path through a recording `GrpcClientInterface` and asserts every invocation received a non-null positive deadline — plus a token-based source scan of the three classes that fails if a *new* call site is added without one; `GrpcClientDeadlineTest` pins the `null` → 30 s resolution (extension-free), and `GrpcClientTimevalDeadlineTest` asserts the resulting `Grpc\Timeval` is not `Timeval::infFuture()` in the ext-grpc `Grpc` suite. - **[PERF-01]**: `RegionResolver::batchResolveRegions()` now reads the region cache before it contacts PD, and bounds the scan it does issue. The method wrote the cache but never read it, so every `batchGet()`, `batchPut()`, `batchDelete()`, `SstIngestor::ingest()`, `TxnReader::batchGet()` and `TwoPhaseCommitter::commit()` — which resolves three times per transaction — paid one unconditional PD `ScanRegions` round trip, and because the call passed `limit = 0` it asked for **every** region between the smallest and the largest key in the request (on a 10 000-region cluster, ~1–2 MB of `metapb.Region` for a single batch). A warm cache now answers a batch with **zero** PD calls. Keys the cache does not hold are grouped into contiguous runs of misses and each run gets one scan: two misses belong to different runs exactly when a cache-served key of the same batch sorts between them, which *proves* a cached region lies strictly between them and so that they cannot share a cache gap — a cold batch therefore still costs exactly one scan, and a batch that straddles two gaps costs two bounded ones. The scan now passes an explicit non-zero `limit` (128 regions per page) and continues from the last returned `endKey` until the requested range is covered, so a scattered batch over a large cluster is paginated instead of answered in one 10 000-region message; every exit of that loop is unconditional (empty page, range reached, non-advancing cursor, short page, and a 1024-page ceiling), so a pathological PD cannot spin it. Finally, a scanned region the cache already holds unchanged is no longer re-inserted — the identity is epoch + range + leader, asked by region ID, so a moved epoch and a leader transfer both still refresh the cache, while a `put()` that only rebuilds the entry (plus its TTL, expiry-heap record and LRU recency) for a region that is already there is skipped. A re-scan consequently no longer extends an unchanged entry's TTL, which is a cost paid at most as one later re-resolution and not a benefit of the skip: the criterion was never about TTL or recency, because the `getByKey()` probe the first version used already refreshed LRU recency on its hit. **Breaking change:** `RegionCacheInterface` gained `getById(int $regionId): ?RegionInfo` (the O(1) counterpart of `getByKey()`, answering with the same leader-aware region and treating an expired entry as a miss); third-party cache implementations must add this method before upgrading. The skip has to ask through *that* method, because the criterion only pays if the probe is cheaper than the write it avoids, and the first version's probe was not: `php benchmarks/BatchResolveRegionsBenchmark.php` (100 already-cached regions against a 10 000-entry warm cache, median of 20) measures an unconditional `put()` at 0.65 ms, that `getByKey()`-based identity check at 1.04 ms — a 1.6× **regression**, the skip costing more than the write — and the shipped `getById()` check at 0.25 ms. So the criterion now buys the write's ~6.5 µs/region (entry rebuild, TTL refresh, expiry-heap push, LRU touch) for ~2.5 µs/region of probe; the three columns are printed side by side. **The fail-closed contract is unchanged**: every key still has to end up in the result map and the first unresolvable key in the caller's order still throws the same `TiKvException` naming it (issue #187), and the miss path keeps the `[minKey, successor(maxKey))` window of #244/#188, which a warm cache must not make optional. Pinned by `tests/Unit/Region/BatchResolveRegionsReadThroughTest.php` (warm cache → no scan, gap-only window with the exact `startKey`/`endKey`/`limit`, one scan per gap, the pagination loop with a test per termination condition, the `put()` skip, and the fail-closed throw), and the #188 E2E vector now reads back through freshly created, **cold** clients, one per read — after #288 its own `batchPut()` warms the cache for every key of the batch, and whichever of the two reads ran first would warm it for the other one, so a warm client computes no window at all and the reverted `[minKey, maxKey)` window would have passed unnoticed. Four `TransactionTest` tests modelled the region cache with `willReturnOnConsecutiveCalls()`, which described a *call order* that the read-through changed; they now share `tests/Unit/Support/StubRegionCache.php`, a stateful in-memory `RegionCacheInterface` that answers from the regions the client actually stored. Measured with `php benchmarks/BatchResolveRegionsBenchmark.php` (median of 20): a 100-key batch over 100 regions against a warm 10 000-entry cache costs 0.67 ms of cache CPU on the pre-#288 path and ~1.0 ms of cache lookups now — the audit's 33.85 ms figure predates #289's cache rewrite, so what this change removes is not CPU but the round trip and the unbounded answer. The read-through's remaining cost is charged **per key and is linear** at ~12 µs/key (1.2 ms at 100 keys, 13 ms at 1 000, 60 ms at 5 000, 120 ms at 10 000, same warm 10 000-entry cache), where the old path paid its `put()`s per *region* — “zero PD calls” is true and does not convey a 120 ms CPU bill for a 10 000-key batch. The benchmark prints that sweep for the record. Recorded for a follow-up rather than fixed here, since it is a logging-policy question and not part of this issue: `RegionCache::getByKey()` builds a `KeyRedactor::redact()` hex string for its debug line on **every** hit, even with a `NullLogger` (measured 1.1–1.6 µs/hit, roughly a tenth of a warm-cache lookup) — a `MetricsInterface`/logging decision about whether a hot lookup should build a redacted key it may never emit. - The declared return type of every public map keyed by a **TiKV key** is widened from `array<string, …>` to `array<array-key, …>`, because `array<string, …>` was false at runtime: PHP has no way to hold the string key `'1000'` in an array, and a canonical decimal-integer key that fits in a PHP int is stored under its `int` form. Measured on PHPStan 2.2.16, the `array-key` alias as written here resolves to a *benevolent* `int|string` in a `foreach`, so that specific call is not flagged today; do not rely on that leniency. Cast with `(string) $k` before handing a key to a `string`-typed parameter — that was already required at runtime, where a `string`-typed consumer under `declare(strict_types=1)` throws a `TypeError`. **No runtime behaviour change**: the coercion is lossless, because PHP casts a string *lookup* the same way it casts the store key, so `$r['1000']` still resolves the entry stored as int 1000, the non-canonical forms (`'01000'`, `'1e3'`) keep their own string entries, and a canonical decimal beyond `PHP_INT_MAX` (`'9223372036854775808'`) is never coerced. ## [v0.6.0] — 2026-09-24

### Changed

- **[PERF-04]**: TxnKV two-phase-commit RPCs are now fanned out across regions instead of issued sequentially — `TwoPhaseCommitter` reuses the `BatchAsyncExecutor`/`GrpcFuture` dispatch-then-wait pattern for prewrite, secondary commits, `batchRollback`, `pessimisticRollbackAll` and the pessimistic-lock first attempts, and `TxnReader::batchGetFromTiKV` dispatches all per-region `KvBatchGet` calls before awaiting any. Commit latency for an R-region transaction drops from `R×RTT_prewrite + RTT_tso + R×RTT_commit` to roughly `RTT_prewrite + RTT_tso + 2×RTT_commit` (10-region transaction at 5 ms/call: ~100 ms → ~30 ms in the test harness; gRPC call count unchanged). All 2PC ordering invariants are preserved: the primary lock is durably prewritten before secondary locks (client-go's rule; async-commit keeps its deliberate primary-last barrier), the primary commit is acknowledged before secondary commits dispatch, secondary commit failures stay logged-and-swallowed with status Committed, and error reporting surfaces the same exception the sequential loop would have thrown first (`BatchPartialFailureException::getFirstRegionError()` now selects the lowest region index, making that contract hold regardless of which region fails in the dispatch phase). ### Added

- **[GAP-04]** (experimental, opt-in): RPC multiplexing over the `BatchCommands` bidirectional streaming RPC. Operations not representable in the `BatchCommandsRequest` oneof (`RawCompareAndSwap`, `RawGetKeyTTL`, `RawChecksum`, `KvGC`, `KvImport`, and any unsupported request type) automatically fall back to the existing unary path, as does the whole fan-out on any stream failure — with the caveat that a fallback re-run of `batchPut` re-extends per-key TTLs (absolute-from-now). This is a per-fan-out batching window, not a background event loop (the PHP grpc extension is synchronous); TxnKV fan-outs and range ops are not multiplexed yet. Correlation, stream reuse, fallback and flag-off identity are unit-tested (fake transport), the ext-grpc-gated tests run in the Grpc suite, and an E2E test validates real stream reuse against a live TiKV (self-skips without a cluster). - **[GAP-02]**: multi-endpoint PD support with leader discovery and failover. `RawKvClient::create()` / `TxnKvClient::create()` accepted an array of PD endpoints but only the first was ever used (`ConnectionFactory` passed `$pdEndpoints[0]` and `PdClient` stored a single immutable address), so the three-node PD cluster deployed for high availability did not protect the client: a routine PD rolling restart, leader election or failure of the single configured endpoint took down every operation — region lookups, store lookups and, because TSO targeted the same address, every transaction begin and commit. `PdClient` now holds all supplied endpoints and a current-address pointer, opportunistically discovers the PD leader via `GetMembers` on the first RPC (preferring the member whose `member_id` matches `leader.member_id` and, among its client URLs, a configured endpoint), and on a transport-level gRPC failure marks the current address bad, re-runs leader discovery across the remaining endpoints and retries against the new leader — at most one pass over the configured endpoints, so an all-members-down scenario propagates the original error after each endpoint was tried once. `TimestampOracle` no longer captures a fixed address: it resolves the PD address per RPC from the same shared source as `PdClient` (so TSO follows the leader) and, on a transport-level TSO failure, invokes a callback that triggers the PdClient failover before the failure propagates — timestamps still fail closed (a locally fabricated timestamp would break MVCC ordering); the next `getTimestamp()` uses the new address. Also pins by regression coverage: commit-phase `KvCommit` `KeyError.retryable`/`KeyError.abort` on the primary region throw `TransactionConflictException` and never mark the transaction committed, and the `commitTs must be set before committing` guard. (#326)

- **[TXN-13]**: the optimistic prewrite lock TTL is no longer hardcoded to 3000 ms; it now scales with the transaction's write-set size as `3000 ms + 10 ms per mutation`, capped at `120000 ms` (mirroring client-go's `maxLockTTL`). A prewrite loop over many regions could exceed the fixed 3000 ms TTL, after which a concurrent reader would roll the still-being-prewritten locks back and the commit failed with `TxnLockNotFound` (a torn transaction). While the prewrite loop runs, `TwoPhaseCommitter` now also heartbeats the primary lock once the elapsed time reaches half of the computed TTL (the window resets after each heartbeat; the heartbeat never runs before the primary region has been prewritten, and with async commit the primary is deliberately prewritten last, so no heartbeat fires before the primary exists — at most one on the primary's final iteration). The pessimistic-lock TTL remains a fixed 30000 ms (out of scope). `Transaction::heartbeat()` is documented as the supported mechanism for application-level long-running transactions, with a recommended 10000 ms advise interval. (#218)

- **[RAW-07]**: decimal-string keys in the associative-array write APIs are now pinned by regression coverage. PHP stores `['12345' => 'v']` with an **int** key, and the string-casts that keep the batch paths working were already shipped in #322 — verified present in `RawKvClient::batchPut()` / `ingest()`, `RawKvBatch::batchPut()` and `SstIngestor::buildPairs()`, so this issue is a duplicate with no production change. (#192)

- **[RAW-06]**: `scan()` / `scanPrefix()` / `reverseScan()` with `limit: 0` now return the complete range instead of silently truncating at the old `MAX_SCAN_LIMIT` (10240) normalisation. `limit: 0` pages internally at 10240 rows per RPC — forward scans continue from `lastKey . "\x00"`, reverse scans move the descending upper bound down to each page's lowest key — and buffers the whole result, so the documented "whole range" contract holds for ranges larger than one TiKV page. Because the full result is still held in memory, the accumulated rows are bounded by the new `options['maxScanRows']` client option (default `RawKvClient::DEFAULT_MAX_SCAN_ROWS` = 100000, must be `>= 1`): exceeding it throws the new `ScanLimitExceededException` (accessors `getMaxRows()`, `getScannedRows()`) instead of truncating. Docs (`README.md`, `docs/getting-started.md`, `docs/operations.md`, `docs/advanced.md`, `docs/configuration.md`, `docs/error-handling.md`, `docs/troubleshooting.md`) describe the new semantics and steer bulk "get all" examples to the iterators. (#191)

- **[TXN-08]**: prewrite now runs inside the transaction's `RetryExecutor`. `TwoPhaseCommitter::commit()` called `prewriteForRegion()` directly in its per-region loop — the only transaction-path RPC not wrapped in the retry executor — so a `NotLeader`, `EpochNotMatch`, `RegionNotFound` or `ServerIsBusy` region error, or a `KeyError.locked` (whose resolved-lock `TxnRetryableException` literally said "retry"), aborted the whole transaction and reached the application. Each region's prewrite is now executed through `RetryExecutor::execute()` with the transaction's classifier, and the region is re-resolved inside the retry closure (`getRegionInfo()` on every attempt) so a `NotLeader` leader switch or cache invalidation is picked up by the next attempt instead of replaying the stale region. Per-region accumulator state (`minCommitTs`, `onePcCommitTs`, `asyncAccepted`) and the async-commit primary-region-last ordering are preserved. Because the prewrite loop is now executor-owned, `RegionErrorHandler::check()` no longer self-invalidates `NotLeader` there (`RetryExecutor::handleNotLeader()` is the sole owner, issue #474), and the prewrite `locked` resolve likewise hands `NotLeader` to the executor. Prewrite is idempotent for a given `start_ts`, so the retry is safe. (#213)

- **[RAW-04] / [REG-05] / [PERF-03]**: region errors carried on a batch response are now retried per region in the wait phase instead of failing the whole call. `RawKvBatch::batchGet()` / `batchPut()` / `batchDelete()` previously wrapped only the dispatch (region resolution + gRPC send) in `RetryExecutor::execute()` and returned an un-awaited `CheckedGrpcFuture`; the response — and therefore every `NotLeader`, `EpochNotMatch`, `ServerIsBusy`, `RegionNotFound`, … — was inspected later by `BatchAsyncExecutor` during its wait phase, outside the retry loop, so a routine leader transfer had zero retries and no cache invalidation. A multi-region `batchGet` turned into a hard `BatchPartialFailureException` and a `batchPut` into an indeterminate partial write that cancelled every other in-flight region. A new `CheckedGrpcFuture::fromRetryableDispatch()` factory issues the first attempt eagerly (preserving the #295 fan-out: every region's send is still stamped before any wait begins) and runs the whole dispatch+await cycle through `RetryExecutor` during the wait, re-resolving the region on every attempt and reusing the executor's per-operation attempt/backoff/deadline budget for the wait-phase retries (the eager first dispatch is issued before the retry clock starts). `NotLeader` with a leader hint now switches the cached leader and other retryable region errors invalidate the region cache; `BatchPartialFailureException` is now raised only after the retry budget is exhausted for a retryable region error (fatal region errors such as `RaftEntryTooLarge` still fail after the first attempt). Response-borne region errors are therefore retried. A top-level non-region `error` string on a `RawBatchPut`/`RawBatchDelete` response (e.g. a TTL/CAS server error) is still surfaced by `RegionErrorHandler::check()` as a bare `RegionException` with no typed error kind, which `ErrorClassifier` classifies as `RegionMiss` — so such strings are retried for up to the backoff budget, exactly as the pre-existing single-key paths (`RawKvCrud::getKeyTTL`, `RawKvAtomic::compareAndSwap`) already behaved; this PR does not reclassify them. No other caller-visible behaviour changes. (#183)

- **[RAW-05]**: `RawKvRangeOps::deleteRange()` / `checksum()` now re-resolve the region inside their retry closures instead of replaying the `RegionInfo` captured before the loop, so retries target the current leader store and pick up `RetryExecutor`'s cache invalidation / leader-switch hints. The `scanRegions()` result is pre-populated into the region cache so the first attempt stays a cache hit (no extra PD `getRegion` round trip). Because of the #295 fan-out only dispatch-phase failures are retried; response-borne region errors surface at wait time as `BatchPartialFailureException`. A region that shrank after enumeration (a split) is rejected by a new `assertRegionCoversRange()` guard: `deleteRange` fails closed, and `checksum` refuses to return a partial result — its raw read is silently clamped by the region snapshot, so a truncated checksum would otherwise be XOR-merged as if complete. The clipped bounds are kept and there is no split-continuation (independent limitation). (#190)

- **[GRPC-10]**: exception messages now redact user keys with `KeyRedactor::redact()`, matching the logging layer. Four sites interpolated the raw key while every surrounding log context redacted it: `RetryExecutor`'s attempt-cap and wall-clock-deadline messages, and `RegionErrorHandler`'s two per-pair (`null` and described) `KeyError` messages. Exception messages are a logging channel (Monolog/Sentry/Bugsnag capture `getMessage()`, uncaught-exception handlers write it to stderr, framework error pages render it), so keys embedding tenant/user IDs, e-mail addresses or session tokens were reaching log aggregation and error trackers unredacted. - **[TXN-09]**: prewrite now fails closed on every `KeyError` variant. `TwoPhaseCommitter::handlePrewriteErrors()` previously handled only `locked`/`conflict`/`retryable`/`abort` and silently treated any other variant — notably `deadlock`, `already_exist`, `assertion_failed`, `primary_mismatch`, `txn_not_found` and `commit_ts_too_large` — as a successful prewrite, so `commit()` proceeded to `KvCommit` even though the prewrite had failed. A `deadlock` now raises `DeadlockException` carrying the deadlock key, key hash and lock timestamp (mirroring the pessimistic-lock path, now shared through `throwDeadlock()`), the remaining named variants raise `TransactionConflictException`, and any unrecognised variant raises a base `TiKvException` described via `KeyErrorDescriber`, so no response can be mistaken for success. (#214)

- **[TXN-25]**: pessimistic-lock acquisition now fails closed on every `KeyError` variant. `TwoPhaseCommitter::pessimisticLockBatch()` handled only `deadlock`/`locked`/`conflict`, so any other variant — `retryable`, `abort`, `already_exist`, `assertion_failed`, `primary_mismatch`, `txn_not_found`, `commit_ts_expired`, … — fell off the end of the per-region error loop with `$needRetry` left `false`, the batch was treated as fully locked, and `commit()` proceeded to prewrite keys whose pessimistic lock was never acquired. `retryable`/`abort` now raise `TransactionConflictException` (mirroring `handlePrewriteErrors()`, #214) and every other variant raises a base `TiKvException` described via `KeyErrorDescriber`, so a `KvPessimisticLock` response can no longer be mistaken for a successful lock. - **[GAP-01]**: TxnKV region lookups now run in the memory-comparable-encoded key space that TiKV uses for transactional region boundaries. `PdClient::getRegion()` / `PdClient::scanRegions()` encode their keys through an injected `CodecInterface` before building the PD request, and `RegionInfoMapper` decodes the returned `start_key`/`end_key` back into user-key space so `RegionCache` keeps comparing user keys, mirroring client-go's `apicodec` (`CodecPDClient`). `RawKvClient::create()` builds its codec with `Mode::Raw` (byte-for-byte passthrough — unchanged behaviour), `TxnKvClient::create()` with `Mode::Txn` (MCE). `MemComparableCodec` now implements TiDB's `codec.EncodeBytes`/`DecodeBytes` faithfully (8-byte groups, marker `0xFF`, final group padded with `0x00` and marked `0xFF - padCount`); the earlier ad-hoc `0x00`/`0xFF` escape scheme was incompatible with TiKV and its `decode` was lossy, stopping at the first `0x00 0x00` inside the encoded boundary (`EncodeBytes("\x01\x00") = 0100000000000000f9` decoded to `\x01`), which both misrouted boundary keys and made multi-region `scan()` fail with `InvalidReqRange`. Decode is now lossless, so cached region boundaries are valid txn scan start keys. Previously the codec layer was dead code and TxnKV sent raw user keys to PD and compared them against encoded boundaries: while the transactional keyspace covered a single region every lookup resolved correctly and the defect was invisible, but once data split across ≥2 regions any key whose raw byte ordering differs from its encoded ordering (or that equals a split boundary) was misrouted and TiKV rejected the request with a fatal `Key ... is out of [region ...]` (KeyNotInRegion-class) error. New unit tests assert the hard-coded MCE vectors, lossless round-trips for binary/trailing-zero/`0xFF` keys, malformed-input errors, that TxnKV PD lookups send encoded keys (and RawKV raw keys), and that boundaries are decoded before caching; the E2E test `TxnKvE2ETest::testTxnWorkloadAcrossPreSplitRegions` pre-splits a fresh cluster into three regions (via the `SplitRegion` RPC, resolving regions through the Txn codec while sending raw split keys) and runs a transactional workload with binary and boundary keys across them, including a forward `scan()`. (#415)

- **[REG-11]**: all `BackoffType` cases now use **equal jitter** — `BackoffType::equalJitter()` returns `true` for every type instead of only `ServerBusy`, `TiKvRpc`, `RecoveryInProgress`, `IsWitness` and `TxnLock`. Previously `NotLeader`, `RegionMiss` and `StaleCmd` (and the remaining types) produced deterministic delays of exactly `min(cap, base * 2^attempt)`; these errors are precisely the ones correlated across a fleet (a leader transfer or region split is observed by every client at nearly the same instant), so every client retried in lockstep at identical offsets against the node that most needed to be left alone. Delays are now drawn uniformly from `[expo/2, expo]`, matching client-go's randomized backoff for `BoRegionMiss`/`BoTiKVRPC`. Behavioural change: retry timing is observable — callers asserting exact sleep durations for previously non-jittered types must assert ranges. `Backoff::exponential()`'s explicit `$equalJitter` argument (default `false`) is unchanged for direct callers. (#242)
- **[REG-12]**: locked in with regression tests that the retry budget is scoped per `RetryExecutor::execute()` call (the accumulator refactor itself landed with #271): a `Transaction` memoizes a single executor for its whole lifetime, so a budget carried across `execute()` calls would be exhausted permanently — every later operation, including `commit()`, would fail on the first retryable error once the transaction had spent its backoff budget. `RetryExecutorTest` now proves both the total backoff budget and the ServerBusy budget reset across sequential `execute()` calls on one executor, and `TransactionTest` proves two sequential operations on the same `Transaction` each get a usable budget (acceptance criteria of the issue). Multi-region RawKV per-region budget semantics (issue #271) are unaffected. (#243)
- **[REG-09]**: `ErrorClassifier` no longer retries every `GrpcException` blindly. The gRPC status code carried on the exception (`GrpcException::$grpcStatusCode`) now drives the retry decision, following standard gRPC retry guidance: `UNAVAILABLE`, `ABORTED`, `INTERNAL`, `UNKNOWN` and `DEADLINE_EXCEEDED` are retried with the `TiKvRpc` backoff, `RESOURCE_EXHAUSTED` gets the `ServerBusy` backoff (subject to its budget), and everything else — notably `UNAUTHENTICATED`, `PERMISSION_DENIED`, `UNIMPLEMENTED`, `INVALID_ARGUMENT`, `FAILED_PRECONDITION` and `CANCELLED` — is fatal and surfaces immediately. Previously a bad TLS/credentials rollout (`UNAUTHENTICATED`) or a gone caller (`CANCELLED`) caused every request to burn ~30 retries with `TiKvRpc` backoff (~30 s and a ~30x cluster-facing load multiplier while failing). Status codes are exposed as the named enum `GrpcStatusCode` (`src/Client/Grpc/GrpcStatusCode.php`); unknown codes fail closed (no retry). `DEADLINE_EXCEEDED` remains retryable because its outcome is indeterminate — the per-operation idempotency distinction is REG-08's scope. Status-code classification runs before any message-text matching, so gRPC detail text cannot be misread as a retryable TiKV region error. (#240)
- **[REG-10]**: `EpochNotMatch` retries are no longer zero-delay and free. The error used to classify as `BackoffType::None` (`sleepMs=0`), so its retries contributed nothing to the backoff budget and the only bound was the 30-attempt cap — during region churn (bulk load, splits, rebalancing) every client hammered PD `GetRegion` and TiKV with back-to-back requests, a metastable-failure pattern. `EpochNotMatch` now maps to a dedicated `BackoffType::EpochNotMatch` with the same values as client-go's `BoEpochNotMatch`: 2 ms base, 500 ms cap, equal jitter, and its sleeps feed the per-operation `totalBackoffMs` budget so persistent epoch errors exhaust the budget instead of only the attempt cap. `BackoffType::None` remains reserved for immediate retry, now used only by the `DataIsNotReady` replica-lag signal (the next attempt targets a different peer). `docs/configuration.md` and `docs/architecture.md` updated. (#241)

- **[REG-13]**: keys whose region cannot be resolved are no longer silently dropped from batch operations. `RegionResolver::batchResolveRegions()` now fails closed — it throws a `TiKvException` naming the first key PD could not map to a region, instead of omitting it (previously `batchPut()` reported success without writing the key and `batchGet()` returned `null` as if the key did not exist). The root cause is also fixed: `scanRegions($minKey, $maxKey)` is half-open and stopped before the region whose `startKey` is exactly `$maxKey`, so a batch's maximum key sitting on a region boundary always failed resolution — the scan now uses `$maxKey . "\x00"` as its upper bound, mirroring client-go's inclusive resolution of the last key. `RegionGrouper::groupKeysByRegionBatch()`, `groupItemsByRegion()` and `TxnReader::batchGetFromTiKV()` additionally throw on an unresolvable key instead of `continue`-ing (defense in depth; the "silently skipped" contract is removed from the docs). Behavioural change: callers that previously received partial results on a PD inconsistency now get an exception. (#244)

- **[GRPC-05]**: the batch dispatch fan-out of `RawKvClient::batchGet()` / `batchPut()` / `batchDelete()` is now bounded. Previously `RawKvBatch` handed one callable per sub-batch (max 512 keys / 16 KB each) to `BatchAsyncExecutor::executeParallel()`, which dispatched **all** of them before awaiting any — a `batchGet` of a million keys put ~1954 gRPC calls on the wire from a single process, holding every serialized request plus future live simultaneously (memory blow-up in PHP-FPM) and saturating the target store's gRPC concurrency pool. `RawKvBatch` now dispatches in windows via `executeParallelCapped()` with the same `maxConcurrency` bound (default 16) already used by the fanned-out range operations (issue #295), configurable through the existing `options['maxConcurrency']` option on `RawKvClient::create()`. Results order, cancellation, deadline and partial-failure semantics are unchanged. (#264)
- **[TXN-10]**: a committed transaction is no longer reported as failed when a **secondary** region commit fails. The transaction status is set to `Committed` immediately after the primary region's commit returns (the commit point), and any failure while committing secondary regions — including `RetryBudgetExhaustedException` and fatal key errors — is logged and swallowed instead of propagating out of `Transaction::commit()`; leftover locks on secondary regions are resolved by other readers, matching client-go. `TwoPhaseCommitter::rollback()` now refuses to run when the status is already `Committed`, so no path can issue `KvBatchRollback` for a committed transaction (the guard is on the status, not `commitTs`: the commit timestamp is already set while the primary commit is attempted, and a failed primary commit leaves a legitimately rollback-able transaction). Behavioural change: callers that previously observed an exception from `commit()` after the primary had committed now see success. (#215)
- **[REG-08]**: `compareAndSwap()` / `putIfAbsent()` no longer retry on transport errors — CAS is not idempotent, so a lost response (e.g. `DEADLINE_EXCEEDED` after the write was applied server-side) followed by an automatic retry would re-send the CAS against the new state and report a false "not swapped" (the distributed-lock caller concludes the lock was not acquired while it in fact holds it). `RawKvAtomic` now passes a custom classifier to `RetryExecutor` that rethrows every `GrpcException` un-retried while delegating region errors (`NotLeader`, `EpochNotMatch`, … — rejected before the write is proposed) to `ErrorClassifier` as before. The indeterminate-outcome contract is documented on `RawKvClient::compareAndSwap()` / `putIfAbsent()`: a thrown `GrpcException` means the outcome is unknown; callers should re-read the key to decide (lock users must treat a throw as indeterminate, never as "not acquired"). (#239)
- **[REG-06]**: the retry wall-clock deadline is now checked **before every backoff sleep** and the sleep is clamped to the remaining budget. Previously the deadline (default 30 s, `options['retryDeadlineMs']`) was only enforced at the top of each attempt, so a single `ServerBusy` backoff sleep (equal-jitter, 10 s cap) could overshoot the configured budget by up to one full backoff interval before the next check ended the loop. When the remaining budget reaches zero during the catch path, the loop now fails immediately with `RetryBudgetExhaustedException` instead of sleeping past it. `RetryExecutor`'s own `$deadlineMs` constructor default changed from `0` (disabled) to `RetryExecutor::DEFAULT_RETRY_DEADLINE_MS` (30 s) — all in-client construction sites already passed a non-zero value since #294, so only direct `RetryExecutor` users are affected. Occupancy worst case is now ≈ deadline + the last in-flight RPC (still bounded only by the gRPC timeout option); the occupancy notes in `docs/configuration.md`, `docs/advanced.md` and `docs/architecture.md` were updated accordingly. (#237)
- **[REG-07]**: `RegionCache::put()` now removes every cached entry whose `[startKey, endKey)` range overlaps the incoming region's range (an empty endKey means unbounded; merely touching ranges are kept). Previously only the entry with the same region ID was removed, so after a region split or merge two entries could claim the same key range and the binary search + insert position logic preferred the stale entry for keys sharing a start key — routing lookups to a region that no longer owns the key (wasted `RegionNotFound` round trip, or fatal `KeyNotInRegion` per REG-02) for the full TTL. `idToIndex` and `lruOrder` stay consistent after removal. (#238)
- **[TXN-11]**: a transport-level failure (`GrpcException`) on the **primary-key `KvCommit`** RPC is now treated as an **undetermined outcome**, not a definite failure (client-go's `ErrResultUndetermined`). `commit()` marks the transaction `TransactionStatus::Undetermined`, closes the state so `__destruct()` can no longer issue a `KvBatchRollback` for a transaction that may already be committed (previously the destructor's rollback raced with a possibly-applied commit and stacked a rollback error on a commit error), and raises the new typed `UndeterminedCommitException` (carrying the original `GrpcException` as `previous`) so the caller can distinguish "unknown outcome" from a definite failure and resolve it out of band. `KeyError`-based commit failures keep the previous definite-failure behaviour. Callers matching exhaustively on `TransactionStatus` must handle the new `Undetermined` case. (#216)
- **[DOC-12]**: `docs/contributing.md` documented the default branch as `main`, but the repository's default branch is `master` (there is no `main`) — the documented first command of every contribution (`git checkout main`) failed with `error: pathspec 'main' did not match any file(s) known to git`. - **SEC-03 (security)**: `RegionResolver` validates every PD-supplied store address before it is used as a gRPC channel target — including the SST ingest `SwitchMode` calls (via the new public `RegionResolver::validateStoreAddress()`). - **SEC-03 (security)**: when neither `allowedStoreHosts` nor `storeHostPolicy` is configured, the client now derives a default store-host policy from the **configured PD endpoints** instead of accepting any bare `host:port`. The host is classified **before** any rule runs: bracketed IPv6 literals are allowed only when byte-identical (`inet_pton`) to a configured PD IPv6 endpoint (zone-id forms like `[fe80::1%eth0]:20160` and IPv4-mapped forms like `[::ffff:10.0.0.1]:20160` are rejected — previously almost any bracketed IPv6 was trusted); IPv4 literals only when equal to a configured PD IPv4 literal or in its /16 subnet (IPs are compared by address bytes and never textually suffix-matched — previously `10.0.0.1` slipped past PD `127.0.0.1` via the shared `.0.1` suffix); digit-leading numeric-IP aliases (`2130706433`, `017700000001`, `0x7f000001`) are rejected outright; DNS names via exact match, single-label (compose/K8s short names such as `tikv1` next to `pd`), or shared last-two DNS labels. (#306)
