### Fixed
- `Transaction::heartbeat()` no longer discards the server's `KeyError` payload when the `TxnHeartBeat` RPC reports a key error — the payload was bound, null-checked, then thrown away behind the constant message `Heartbeat failed: key error`, so an operator debugging a long-running transaction (the primary heartbeat use case) could not tell whether the server had GC'd the transaction (`txn_not_found`), lost its lock (`txn_lock_not_found`), or reported a conflict. `retryable`/`abort` variants now surface as `TransactionConflictException` carrying the server's text, a `locked` response as `TxnRetryableException` (deliberately **not** resolved: the only lock a heartbeat can report is the calling transaction's own primary lock, and resolving it would roll the calling transaction back underneath itself), and every other variant falls back to a base `TiKvException` whose message names the variant via the new shared `KeyErrorDescriber` (extracted from `RegionErrorHandler`, so the region-error per-pair messages stay byte-identical). (#492)

- **[DOC-38 follow-up]**: `docs/advanced.md`, `docs/architecture.md` and `docs/configuration.md` no longer understate the retry wall-clock deadline (`retryDeadlineMs`, #294) as overshooting "by at most one backoff sleep". The deadline is checked only **before each attempt** (`RetryExecutor`, `$elapsedMs >= $this->deadlineMs` guard at the top of the loop), so a worker's real occupancy can exceed it by one final backoff sleep (**up to ~10 s under ServerIsBusy**) plus the full wall time of the last in-flight RPC — bounded only by the gRPC timeout option (`options['timeout']`), not by the retry deadline. All three files now carry the same corrected wording plus a worked example (`retryDeadlineMs => 1000` with a 5 s RPC ⇒ real occupancy ≈ 6 s + sleep) so operators tuning the deadline for PHP-FPM occupancy plan the true worst case. - **[DOC-39]**: the documentation now states that RawKV TTL mode and TxnKV are mutually exclusive. A TiKV cluster with `[storage] enable-ttl = true` runs in V1TTL storage mode, which serves RawKV with TTL but **not** transactional requests — a single cluster cannot serve both (TiKV's `APIVersion.V1TTL` accepts only raw requests). The docs already carried the data-wipe-on-toggle caveat; changing the setting on a live cluster is an operational migration. (#405)
- **[DOC-26]**: `docs/advanced.md` no longer teaches a hand-rolled user-level retry loop (`withRetry()` + `isRetryable()`) around every client call. The client already retries all transient errors internally (`NotLeader`, `EpochNotMatch`, `ServerIsBusy`, `StaleCommand`, `RegionNotFound`, gRPC transport errors) through a bounded `RetryExecutor` — an outer loop multiplies the total wait (the inner executor can already spend up to 30 attempts / 30 s wall-clock on one operation) and can pin PHP-FPM workers far longer than either layer intends. The "Retry Strategies" chapter now opens with a "You do not need your own retry loop" warning, a budget table with the real defaults and source constants (30 attempts / 20 s cumulative backoff / 60 s ServerBusy budget / 30 s wall-clock deadline from #294), documents which budgets surface `RetryBudgetExhaustedException` (`attempts()`, `elapsedOrBackoffMs()`, `getPrevious()`) as a hard failure — attempt cap and deadline — versus the two sleep budgets whose exhaustion rethrows the original TiKV error, and links the full reference in `docs/configuration.md#retry-and-backoff`. (#392)
- **[OBS]**: `MetricsInterface::regionInvalidated()` is now emitted from every `RegionCache::invalidate()` drop path instead of a single one (TTL-expiry sweeps and LRU eviction intentionally do not count as invalidations), so dashboards built on `region_invalidations_total` no longer undercount. `RegionCache::invalidate()` is the single emission point: it accepts an optional `$reason` (default `'region_error'`), and emits exactly once per **actual** removal — invalidating an ID that is not cached emits nothing. Reasons: `'retry_region_error'` (RetryExecutor pre-retry invalidation — previously the only emitting site), `'not_leader'` (`RetryExecutor::handleNotLeader()` hint-unknown/no-hint drops — the sole owner of NotLeader drops at executor-owned call sites; the few txn call sites with no retry executor around them — commit()'s prewrite loop, `pessimisticLockBatch()`, `Transaction::batchGet()` — self-invalidate inline via `RegionErrorHandler::check(..., notLeaderOwnedByRetryExecutor: false)`, restoring master's stale-entry recovery), `'lock_resolve'` (`LockResolver::invalidateRegionFor()`), `'region_error'` (all other top-level region errors via `RegionErrorHandler::check()`). `RawKvClient::create()`/constructor and `TxnKvClient::create()`/constructor attach the configured metrics backend to the region cache automatically via the new in-place `RegionCache::attachMetricsIfAbsent()` (an explicitly attached backend wins; shared caches are mutated, never cloned or rebound); caches without a backend stay zero-cost (no-op). A NotLeader response with a still-valid hinted peer only switches the cached leader and emits nothing. The `MetricsInterface::regionInvalidated()` docblock now documents the real contract. (#474)

- **[LQ-01]**: the four `LockResolver` tests for the lock-resolution paths (`testResolveLockWithCommitTsGetsCommitted`, `testResolveLockWithZeroCommitTsRollsBack`, `testResolveLockWithActiveLockWaitsThenRollsBack`, `testResolveLockWithLockActionImmediatelyRollsBack`) now assert what the code actually does instead of only counting gRPC calls. The committed and rolled-back branches build the same `ResolveLockRequest` and issue the same `KvResolveLock` RPC; the only difference is one field — `setCommitVersion($commitTs)` versus `setCommitVersion(0)` — so swapping the two private resolve methods previously left all four tests green while silently inverting commit-versus-rollback behaviour on the transaction-recovery path (resolving a committed lock as rolled back destroys committed data; the reverse makes an aborted transaction's writes permanently visible). ### Changed
- **[PERF-08]** (#295): `RawKvRangeOps::deleteRange()`/`deletePrefix()`/`checksum()`, `RawKvScanner::batchScan()` and `SstIngestor::switchStoresMode()` now issue their per-region/per-store RPCs concurrently instead of serially. The wire sends are fanned out (all sends in a window are issued before any wait begins, so server-side latencies overlap), bounded by a concurrency cap — default **16** — configurable via `options['maxConcurrency']` on `RawKvClient::create()` (or the corresponding constructor argument; must be `>= 1`). Refactorings: a new `BatchAsyncExecutor::executeParallelCapped()` (windows of at most `$maxConcurrency` in-flight requests through the existing executor) and a new `GrpcClientInterface::callAsync()` (issue a unary send without waiting; response resolved later via `GrpcFuture`). `SstIngestor` dispatches every store's SwitchMode request before awaiting any. **Behaviour change:** a partial failure now surfaces as `BatchPartialFailureException` (aggregating every failing region) instead of aborting at the first failing region; `deleteRange`/`checksum` remain idempotent so retrying the whole operation is safe. (#295)
- **[PERF-07]**: the blocking retry backoff is now bounded by a wall-clock deadline by default, so a sustained `ServerIsBusy` episode can no longer pin a PHP-FPM worker for minutes inside a single request. `RawKvClient` and `Transaction` construct their `RetryExecutor` with a non-zero `deadlineMs` (default **30 s**, previously disabled — the only bounds were a 10-minute ServerBusy budget and the attempt cap, so one request could block for up to ~10 minutes). The deadline is configurable via the new `options['retryDeadlineMs']` on `RawKvClient::create()`/`TxnKvClient::create()` (and the corresponding constructor argument; `0` restores the old unbounded behaviour — not recommended under PHP-FPM), and is threaded into every retry executor the client builds, including the scan and range paths. The default `serverBusyBudgetMs` is reduced from 600 s to **60 s** (order-of-magnitude cut; it acts as a worker-occupancy setting, not a cluster-recovery horizon) and documented as such in `docs/configuration.md`. **Behaviour change:** operations that would previously have eventually succeeded after minutes of blocking backoff may now fail fast with `RetryBudgetExhaustedException`; this trade is intentional — bounded per-request latency and fast failure beat pool exhaustion during a TiKV degradation. (#294)

### Fixed
- **[CI]** (#485): the CI `Lint` gate is green again — rector 2.6.x (resolved fresh by CI's `composer install`; no lock file is committed) flagged eight files that the locally-pinned rector did not, failing every PR's lint. Six `src/Client` files are updated to the idiomatic `??=` null-coalescing-assign form (`IfToNullCoalescingAssignRector`), and rector is configured (`rector.php` `->withSkip()`) to leave two test classes alone because every transform rector 2.6 proposes for their `setUp()`-initialised properties breaks them: `ReadOnlyPropertyRector` + `RemoveUnusedPrivateMethodRector` deletes the `setUp()` that initialises the now-readonly props (leaving them uninitialised → "must not be accessed before initialization" errors in all 24 tests), and `PrivatizeFinalClassMethodRector` makes `setUp()` private, which PHPUnit rejects with a fatal "must be protected" error. Files: `RegionCache.php`, `RawKvBatch.php`, `SstIngestor.php`, `RegionGrouper.php`, `TwoPhaseCommitter.php`, `TxnReader.php` (mechanical `??=`), `rector.php` (skip list).
- `LockResolver::resolveLock()` no longer blocks for up to the full `maxBackoffMs` (20 s by default) on a still-active lock: the TTL wait sleep is now capped by an optional `$remainingDeadlineMs` parameter, and `TwoPhaseCommitter::pessimisticLockBatch()` passes its remaining pessimistic-lock budget into it and charges the wall time spent resolving (status RPCs + wait) back into `$elapsedMs`. Previously the lock wait was charged to no budget — invisible to both the pessimistic-lock budget (which could silently stretch past `maxBackoffMs`) and, when reached inside retry closures, to the RetryExecutor wall-clock deadline from #294. Callers that pass no remaining deadline keep the old uncapped-by-deadline behaviour; the read/scan/prewrite/rollback call sites are intentionally unchanged — their waits overshoot the #294 deadline by at most one resolve, detected at the next inter-attempt check. (#470)
- **[SEC-02]**: `TlsConfigBuilder` no longer silently reinterprets an unreadable certificate **path** as inline PEM content. The deprecated guessing methods (`withCaCert()`, `withClientCert()`) previously flipped from "read the file" to "treat the path string as the certificate body" whenever the file was missing or unreadable, so `TlsConfig::isEnabled()` still returned `true` and the client logged `tls: true` while gRPC could fall back to a plaintext channel — an invisible downgrade. A value that looks like a path (does not contain `-----BEGIN`) whose file does not exist or is not readable now throws `InvalidArgumentException` at construction time instead of connecting insecurely. `TlsConfig` now also rejects any certificate/key material that does not contain a PEM header. The docs and example now demonstrate the explicit `caCertFile`/`clientCertFile`/`caCertBaseDir` (and `*Pem`) options instead of the deprecated `caCert`/`clientCert` keys. (#305)
- **TEST-14 / CI-03**: fixed a failing `Integration` test and wired the suite into CI. `testRegionCacheInvalidationLogContainsRegionId` stubbed the second `grpc->call()` with a `RawGetResponse` while driving `RawKvClient::put()`, so the typed closure in `RawKvCrud::put()` threw a `TypeError`; the `Integration` suite (declared in `phpunit.xml`) was red with nobody running it. The stub now returns `RawPutResponse` as `put()` expects, and the test asserts the invalidation log carries both the `regionId` context field and the message identifying the reason (`Invalidated region on retry`). The previously-red `Integration` suite now exits 0 locally (`vendor/bin/phpunit --testsuite Integration`). A new `integration-tests` CI job runs the suite on every PR with `--fail-on-skipped`. (#334, #360)
- **[TEST-12]**: `RawKvScanner::validateScanLimit()` now rejects negative limits with `InvalidArgumentException('Scan limit must be 0 or greater')` before they reach `RawScanRequest::setLimit()`, a `uint32` protobuf field where `-1` serialises to `4294967295`. Previously a negative limit (from user input, a decremented counter, or an off-by-one) bypassed `MAX_SCAN_LIMIT` and became an effectively unbounded scan that could OOM the PHP worker and sustain heavy load on the TiKV cluster. The error message is now byte-identical to `TxnReader::normalizeScanLimit()`, so the two scan paths agree. Regression tests cover every public scan entry point (`scan`, `reverseScan`, `scanPrefix`, `batchScan`, `scanIterator`, `scanPrefixIterator` on `RawKvScanner`/`RawKvClient`, and `Transaction::scan`), the boundary values 1 / `MAX_SCAN_LIMIT` / `MAX_SCAN_LIMIT + 1`, and the cross-path message agreement. (#332)
- **GRPC-12 (retry)**: `RetryExecutor::execute()` now treats its backoff budget as **per-operation** — the `attempt`, `totalBackoffMs` and `serverBusyBackoffMs` counters were instance fields that never reset between calls, so a single executor reused across many operations (memoised in `Transaction::retryExecutor()`, once per region in `RawKvScanner::scan()`, once per sub-batch in `RawKvBatch`) silently carried its spent budget forward. Once the accumulated total crossed `maxBackoffMs`, every later operation failed on its first retryable error without retrying; a long transaction degraded into no-retry mode and large batches became progressively more fragile. The three counters are now per-invocation local state inside `execute()`, so every call starts with a full budget and `execute()` is reentrant — the executor can be reused safely. **Backward-compat note:** operations that previously failed early now retry as documented; overall latency under sustained cluster errors may increase, which is the intended behaviour (bounded by the attempt cap and per-call deadlines). Regression tests cover a reused executor retrying normally on its second call and a multi-region scan retrying with a fresh budget per region. (#271)
- **[GRPC-09]**: `GrpcClient::getChannel()` now throws `InvalidStateException` when called on a closed client, matching the guard already present in `call()`/`callStreaming()`. Previously a `getChannel()` after `close()` silently opened fresh channels and stored them in the never-again-drained channel map, leaking sockets and memory until `RLIMIT_NOFILE` — reachable via the `RawKvBatch` path or any retained `GrpcClient` reference. `close()` now drains the channel map unconditionally regardless of the internal closed flag, and `closeChannel()` is a no-op on a closed client, so a closed client can never hold a channel. **Backward-compat note:** code that called `getChannel()` after `close()` now throws instead of silently leaking; that code was already broken — the exception makes it visible. (#268)
- **[GRPC-07]**: `GrpcClient::call()` now starts its RPC latency timer **before** the blocking `startBatch()` send/receive calls and wraps channel acquisition, call construction and both batches in the `try`/`finally` so send-phase failures also record `rpcCompleted` (with `success=false`). Both `call()` and `callStreaming()` now use the monotonic clock `hrtime(true)` instead of wall-clock `microtime(true)` so NTP steps cannot produce negative durations, and both measure the same span. Previously `call()` assigned `$startMs` after the round-trip had already completed, so `MetricsInterface::rpcCompleted()` reported tens of microseconds regardless of actual network latency — dashboards and alerts built on it never reflected real TiKV latency. Reported latency values will now increase to their true scale; review alert thresholds on deploy. (#266)
- Region-boundary key routing now compares keys in **byte order** (`strcmp`), matching TiKV's region split semantics, instead of PHP's `<`/`<=`/`>=` string operators, which compared numeric-looking strings numerically. Numeric-string keys (user IDs, order IDs, epoch timestamps) can no longer be silently mis-routed to the wrong region — misplaced `batchPut`/`batchGet` writes, dropped keys in batches, and reversed/empty scan sub-ranges. Applies to `RegionCache`, `RegionResolver`, `RegionRangeClipper`, `RawKvBatch::keyInRegion` and `ScanIterator`. (#321)
- **[GRPC-08]**: `RawKvClient::scan()`/`reverseScan()` and `TxnKvClient::scan()` now re-resolve the region **inside** the retry closure instead of capturing a `RegionInfo` resolved before the retry loop. Previously, after `NotLeader` or `EpochNotMatch` the retry executor invalidated the cache and switched leader hints, but the closure re-sent the same stale region tuple, so every retry reproduced the original error until the attempt cap (up to 30 RPCs against a store that had already reported an error). Scans now pick up invalidation/leader switching like the single-key and batch paths already did. When a retry resolves a post-split region narrower than the requested sub-range, the scan **continues from the fresh region's end key** (forward) or prepends the higher remainder (reverse) so no part of the original range is silently dropped; the region cache is populated from the `scanRegions()` result on every scan so first attempts hit the cache. (#267)
- `make test-e2e` / `composer test:e2e` previously invoked a non-existent PHPUnit suite `E2E` (`phpunit.xml` defines `E2E-RawKV` and `E2E-TxnKV`), so the local E2E runner executed zero tests. `scripts/test-e2e.sh` now mirrors CI — RawKV E2E on the V1ttl cluster, then TxnKV E2E on the V1 cluster (txnkv compose override) — and `composer test:e2e` targets the existing RawKV suite. (#267)
- Numeric-string keys (`'12345'`, `'0'`) now work across TxnKV and RawKV read/write paths. Previously PHP's integer-like array-key coercion made `$txn->set((string) $userId, $payload)` throw a raw `TypeError` (uncatchable as `TiKvException`) at commit time — `TransactionState::getPrimaryKey()`/`getWriteKeys()` returned `int` keys — and `RawKvClient::batchPut(['12345' => 'v'])` failed validation the same way; transaction `batchGet()`/`scan()` were also affected. Keys are now string-cast at every typed consumption point (state accessors, prewrite mutations, batch region resolution, `KvPair`/`Pair` wire construction) and the batch APIs accept `string|int` keys, rejecting any other type with `InvalidArgumentException`. (#322)
- `Transaction::commit()` now throws a `LockWaitTimeoutException` (carrying the key and the backoff budget) when pessimistic lock acquisition exhausts its retry budget (`maxBackoffMs`), instead of silently continuing to prewrite without the locks — the transaction can no longer proceed/commit with lost or conflicting lock state. The exception message shows the key **redacted** via `KeyRedactor`; the raw key stays available through `getKey()`. (#219)
- **SEC-03 (security)**: `RegionResolver` validates every PD-supplied store address before it is used as a gRPC channel target — including the SST ingest `SwitchMode` calls (via the new public `RegionResolver::validateStoreAddress()`). Any address that is not a bare `host:port` (bracketed IPv6 `[addr]:port` accepted) is unconditionally rejected with a distinct `InvalidStoreAddressException` (logged at error level): `unix:`, `unix-abstract:`, `dns:///` schemes, a host that is itself a reserved gRPC/URI scheme name (`unix:20160`, `dns:20160`, `ipv4:20160`, `vsock:20160`, … — rejected case-insensitively so grpc-core never interprets the address as a URI at `new Channel()`), trailing-newline suffix tricks (anchored `\A…\z` regex), and out-of-range ports (0 or 65536+) can no longer reach the channel constructor. `InvalidStoreAddressException` is classified as fatal in `ErrorClassifier` before any message matching, so an address text containing retry keywords (e.g. `EpochNotMatch`) can no longer trigger up to 30 retries that hide the rejection. Prevents a rogue or on-path PD from redirecting the client — and the data it writes — to an arbitrary host, port or local Unix socket. (#306)
- **SEC-03 (security)**: when neither `allowedStoreHosts` nor `storeHostPolicy` is configured, the client now derives a default store-host policy from the **configured PD endpoints** instead of accepting any bare `host:port`. The host is classified **before** any rule runs: bracketed IPv6 literals are allowed only when byte-identical (`inet_pton`) to a configured PD IPv6 endpoint (zone-id forms like `[fe80::1%eth0]:20160` and IPv4-mapped forms like `[::ffff:10.0.0.1]:20160` are rejected — previously almost any bracketed IPv6 was trusted); IPv4 literals only when equal to a configured PD IPv4 literal or in its /16 subnet (IPs are compared by address bytes and never textually suffix-matched — previously `10.0.0.1` slipped past PD `127.0.0.1` via the shared `.0.1` suffix); digit-leading numeric-IP aliases (`2130706433`, `017700000001`, `0x7f000001`) are rejected outright; DNS names via exact match, single-label (compose/K8s short names such as `tikv1` next to `pd`), or shared last-two DNS labels. Anything else is rejected with a logged `InvalidStoreAddressException`, closing the rogue-PD TCP-redirect hole by default; an explicit `allowedStoreHosts`/`storeHostPolicy` still overrides the default. (#306)
- **SEC-03 (security, round 3)**: the shared last-two-DNS-label suffix rule now applies **only** when the configured PD host is a real dotted DNS name — PD endpoints that are IPv4/IPv6 literals (`inet_pton`), digit-leading numeric aliases (`123.456.789`) or single-label names no longer contribute a suffix, so with PD at `10.0.0.1:2379` the store address `attacker.0.1:20160` is rejected (previously accepted via the textual `.0.1` suffix). The reserved gRPC/URI scheme rejection list now also covers the resolver schemes registered by grpc-core 1.80 — `xds`, `google-c2p`, `google-c2p-experimental` (`xds:20160` etc. previously passed the format check and reached `new Channel()`). Store **ports** are now part of the trust decision: under the default PD-derived policy the address port must be `>= 1024` unless explicitly listed in the new `options['allowedStorePorts']`, and when that option is set the port must be in it (applies to every default-policy branch: exact PD host, /16, single-label, suffix). (#306)
- `LockResolver::checkTxnStatus()` no longer sends `hrtime()`-derived values as MVCC timestamps: `caller_start_ts` is now the resolving transaction's PD-allocated `start_ts` and `current_ts` is a freshly allocated PD TSO timestamp (fetched with a finite timeout). The old values were nine orders of magnitude below genuine TSO timestamps, so TiKV could never conclude that an abandoned lock had expired, blocking every later reader of the affected keys. `LockResolver`'s constructor now takes `PdClientInterface $pdClient`, `int $callerStartTs` and `TimeoutConfig $timeoutConfig` (internal collaborator, not public API). (#270)
- `Transaction::commit()` no longer allocates a new commit timestamp when retried after a failed commit phase — the stored commit timestamp is reused, eliminating the risk of a transaction being committed at two different timestamps (partial-transaction visibility window). (#217)

### Fixed
- **Batch operations now issue all per-region gRPC sends before any wait begins** — `RawKvBatch`'s `batchGetWithRetry`/`batchPutWithRetry`/`batchDeleteWithRetry` previously called `$future->wait()` inside the retry closure, which meant the public `BatchAsyncExecutor::executeParallel` always received already-resolved values and the genuine fan-out path (`executeBatch*ForRegionAsync()` returning un-waited `GrpcFuture`s) was dead code. Each call now returns an un-waited `GrpcFuture` wrapped in `CheckedGrpcFuture`, so every region's gRPC send RPC is dispatched in the executor's dispatch phase (true client-side fan-out at the wire layer) before the executor's wait phase collects responses in declaration order. - Removed dead runtime guard in `batchScan()` that was suppressed with `@phpstan-ignore`; the PHPDoc type `array<array{0: string, 1: string}>` already guarantees the contract, and malformed input now produces a `TypeError` instead of `InvalidArgumentException` (#112)
- `getKeyTTL()` now validates key (empty/oversized), consistent with `get()`, `put()`, `delete()` (#109)
- `deletePrefix()` now rejects prefixes consisting entirely of 0xFF bytes, which would previously delete to the end of the keyspace instead of just the intended range (#105)
- Replaced `array_merge` in scan loops with `array_push` to avoid O(n²) copying across regions (#97)
- `getPrimaryKey()` now uses `array_key_first()` instead of `array_keys()`, avoiding O(n) memory allocation on every call (#114)
- PHPStan analysis now sets an explicit memory limit of 1G, preventing crashes with the default 128M limit (#115)
- Raw keys are now automatically redacted in log context across `RegionCache`, `RetryExecutor`, `Transaction`, and `LockResolver` — added `KeyRedactor` utility that replaces raw keys with a hex prefix + length, preventing sensitive-data leakage into log aggregation. A custom redaction callable can be injected via `KeyRedactor::setRedactor()`. (#88)
- `get()`, `batchGet()`, and `Transaction::get()` now correctly distinguish empty-string values from missing keys by checking the response's `not_found` flag instead of treating empty values as null (#77)
- `batchPut()` with a scalar TTL now expands the TTL to one element per pair instead of sending a 1-element array for an N-key batch, ensuring every key receives the intended expiry (#78)
- `LockResolverTest` now executes (all 11 tests) instead of erroring on every method — replaced `createMock()` of generated protobuf messages with real `CheckTxnStatusResponse`/`ResolveLockResponse` instances constructed via setters, restoring coverage of the commit/rollback/wait/region-error decision matrix (#99)
- `close()` is now exception-safe across `GrpcClient`, `RawKvClient`, and `TxnKvClient` — a throw from one channel/sub-client no longer leaks the rest or leaves the client in a non-idempotent state (#107)
- `RetryExecutor::execute()` is now bounded by a configurable attempt cap (`maxAttempts`, default 30) and an optional wall-clock deadline (`deadlineMs`), independent of accumulated backoff. Previously, errors classified as `BackoffType::None` (e.g. `EpochNotMatch`) returned `sleepMs=0`, so `totalBackoffMs` never grew and the `while (true)` loop drove an infinite zero-sleep 100%-CPU busy loop. New exhaustion throws `RetryBudgetExhaustedException` (extends `TiKvException`) (#72)
- Corrected `CHANGELOG.md`, `README.md`, and `docs/configuration.md` to reference actual APIs, constants, and file paths instead of nonexistent ones (`GrpcClient::setTimeout()` → `TimeoutConfig`/`options['timeout']`, `MAX_RAW_SCAN_LIMIT` → `MAX_SCAN_LIMIT`, removed dead `RegionContext.php` and `docs/superpowers/` link, moved shipped "In Progress" features to "Recently Completed", clarified env var usage as application-level wiring) (#101)
